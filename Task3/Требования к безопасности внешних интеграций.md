## Требования к безопасности

- все данные, обрабатываемые в процессе взаимодействия с внешними сервисами должны быть зашифрованы (использование https с tls 1.3)
- `smart-access-gateway` должен использовать таймауты и паттерн circuit breaker при обращении к внешнему сервису для снижения риска ddos атак
- все вызовы к API должны логироваться, логи должны быть структурированными, сегментированными (к примеру, по типу устройства) и достаточно детализированными. (Иcпользовать JSON schema при первичном тестировании структуры логов)
Логи должны содержать как минимум метку времени, тип и id события, пользователя и токен устройства. Логировать события упарвления устройствами, получения доступа к потоку данных устройств, аутентификации и авторизации, административных действий, платежей. Логи должны быть максимально обезличены
- следует внедрить систему централизованного сбора и анализа журналов, систему корреляции событий и реагирования на аномалии (SIEM с оповещениями, автоматической блокировкой доступа)
- журналы следует хранить в отдельном сегменте сети, все журналы должны быть зашифрованы ключами безопасности, должна производиться регулярная ротация ключей
- необходимо предусмотреть ротацию и архивирование журналов, удаление уже неактуальной информации
- внедрить систему мониторинга метрик утилизации ресурсов, количества ошибок, времени отклика. Настроить алертинг на основе
- настроить систему разграничения доступа по управлению умными устройствами
- управлять целостностью передаваемых данных на основе HMAC механизма
- внедрить MFA для пользователей
- Максимально исключить персональные данные при передаче запросов во внешние сервисы
- использовать Cookie, помеченные Secure меткой

### Протоколы аутентификации и авторизации
- По возможности использовать mTLS для двусторонней проверки для соответствия принципу ZeroTrust. В противном случае использовать OAuth 2.0 Client Credentials Flow
- Обеспечить шифрование (с ключами в KMS) и безопасное хранение секретов и/или сертификатов, их обновление
- На стороне системы и собственника использовать OAuth 2.0 c OIDC, также обеспечить контроль прав доступа к устройствам на уровне сервиса


## Взаимодействие между системами предприятия и внешней платформой

- Все запросы (предварительно прошедшие авторизацию в соответствующем сервисе) от собственников идут через сервис `smart-access-gateway` посредством синхронных REST запросов
- `smart-access-gateway` проверяет доступ на основе политик использования устройством, если доступ разрешен отправляет запрос к внешнему сервису, устанавливая соединения на основе двунаправленной проверки сертификатов
- `smart-access-gateway` получает данные о политике пользования устройств асинхронно от CRM, которая уже рассылает данные посредством CDC
- в случае предоставдения видео для домофона - `smart-access-gateway` отправляет готовую ссылку с сервиса партнера для установления прямого соединения для получения видеопотока
- `smart-access-gateway` журналирует все события связанные с доступом или применением команд к устройству в шифрованной БД с механизмом CDC для централизованного сбора и анализа
- `smart-access-gateway` может получать события из внешнего сервиса (в т.ч. с использованием вебхуков) для оповещения пользователей посредством шифрованного WS соединения
